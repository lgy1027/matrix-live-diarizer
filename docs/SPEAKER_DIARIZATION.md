# 说话人识别能力边界

> **写在前面**：本项目同时支持**实时 WebSocket** 和 **上传离线处理**。实时模式是单麦克风、短语音段、低延迟架构，适合字幕和参考性说话人标签；上传离线模式可以拿到完整音频，因此可以启用 pyannote 做更高准确度的后处理 diarization。本文帮你理解**能做到什么、做不到什么、怎么绕过**。

## TL;DR

| 你的场景 | 准确度 | 怎么做 |
|---|---|---|
| 单人独白（网课、播客、直播字幕） | **95%+** | 默认实时模式，开箱即用 |
| 2-3 人会议（每人说话 ≥ 2s，安静） | 60-80% | 实时模式 + 给每个人手动 enroll |
| 3-10 人会议（单麦克风，实时） | 40-60% | 仅作参考性字幕，不要当作精确 diarization |
| 3-10 人会议（**离线高准确度**） | **80%+ DER** | 上传文件 + `?diarization=pyannote` |
| 多人精确识别（生产级） | — | **物理上需要多麦克风阵列** |

---

## 为什么单麦克风实时多人会议做不到精确？

### 物理限制

单麦克风录音 = 一个时间序列音频信号。多人说话时，所有人的声音**叠加**成一段波形。算法无法区分"这段能量是 A 还是 B 说的"——除非有额外信息。

**类比**：你在一间房里只有一只耳朵，听到 3 个人同时说话时，你也只能靠**音色、语调、内容上下文**猜测谁在说话——而且经常猜错。

要"听得清"，要么：
- **多麦克风阵列**（空间信息 → beamforming → 分离声源）
- **接触式麦克风**（每人戴领夹麦 → 物理隔离声源）

### 模型限制

| 模型 | 训练数据 | 能力 |
|---|---|---|
| CamPlus（声纹） | VoxCeleb（清晰单人录音） | 区分说话人**音色**;但当声音叠加成混叠，cosine 距离波动 0.3-0.6，>0.5 误判严重 |
| Qwen3-ASR（转写） | 多说话人数据集少 | 假设"一段一人";多人同时说直接丢失 |
| pyannote 3.1（业界 SOTA） | AMI/AISHELL-4 多人会议 | **离线** 5s 窗口 + spectral clustering;实时做不到 |

> 注意：ASR 负责把语音变成文字；说话人识别由 CamPlus/ERes2NetV2/Wespeaker 声纹引擎或上传离线 pyannote 完成，不是 Qwen3-ASR / Paraformer 自带的能力。

### 实时约束

实时模式 ASR 必须 0.5-5s 出结果——没有长上下文（如 60 秒整段）可做**后处理聚类**。离线模式上传完整文件后才能跑 spectral clustering / VBx 这类算法（pyannote/NeMo 都这么做）。

## 实时模式说话人识别的工作原理

### 流程

```
浏览器麦克风
    ↓ (16kHz mono)
WebSocket 流
    ↓
VAD 分段 (0.5-5s/段)
    ↓
ASR 转写 (Qwen3-ASR)
    ↓
CamPlus 提取声纹 embedding
    ↓
ChromaDB cosine 匹配:
    - best_dist < 0.42: 高置信度 → MATCHED
    - 0.42-0.50: 边缘区 → EDGE OK
    - > 0.50: 新说话人 → 创建 Spk_xxx
```

### 关键阈值

| 段长 | LOW 阈值 | HIGH 阈值 | 行为 |
|---|---|---|---|
| < 0.3s | — | — | skip,标 `Spk_unknown` |
| 0.3-2.0s | 0.55 | 0.75 | 宽松匹配,几乎永远合并到现有 Spk |
| ≥ 2.0s | 0.42 | 0.50 | 严苛匹配,可能创建新 Spk |

**为什么短段宽松、长段严格？**
- 短段（< 2s）embedding 不稳定，cosine 距离波动 0.5+ 是常态
- 长段（≥ 2s）embedding 稳定，能真正判定说话人

### 短段永远合并的副作用

**好处**：单人独白时，"嗯/对/好的"等短回应会自动合并到主说话人，不会被错误识别为新说话人。

**坏处**：多人会议时，A 和 B 的短回应可能被错误合并到同一个人（因为宽松阈值）。

## 怎么最大化准确度

### 1. 单人独白场景

- ✅ 实时模式开箱即用
- ✅ 建议在 Voice Library 给自己的声音 **enroll**（增加识别稳定性）

### 2. 2-3 人小会议

- ✅ 给每个参与者**手动 enroll**（录制 5-10 秒样本 + 命名）
- ✅ 让每人说话 ≥ 2 秒（VAD 切出长段）
- ✅ 会议中保持 ≥ 1 秒停顿（让 SILENCE_THRESHOLD_FRAMES 触发）

### 3. 3-10 人会议（单麦克风）

- ⚠️ **实时模式只能做参考性字幕**，不要指望精确区分
- ✅ 推荐场景：
  - **直播/网课字幕**（主播独白为主）
  - **会议快速纪要**（配人工校对）
- ❌ 不推荐：法律/医疗/金融会议纪要

### 4. 3-10 人会议（多麦克风）

- 🎯 每人一麦 + 每人 enroll = **85%+ 准确度**
- 局域网固定参与者的小团队适用

### 5. 离线高准确度（推荐：上传录音）

- ✅ 集成 pyannote 3.1（业界 SOTA，Diarization Error Rate ~18%）
- ⏱️ 延迟 2-5 秒（需整段音频后处理）
- 🎯 适用：会议后整理、需要精确分段

## 离线模式 vs 实时模式 怎么选

| | 实时模式 | 离线模式 |
|---|---|---|
| 延迟 | ~500ms | 2-5s |
| 输入 | WebSocket 音频流 | 上传完整音频文件 |
| 说话人识别 | CamPlus（短段波动） | pyannote 3.1（SOTA） |
| 适合 | 字幕、即时反馈 | 会议纪要、归档 |
| 资源占用 | 低（CPU 实时） | 高（GPU 推荐） |

一句话：**实时模式先保证快，上传离线模式先保证准**。多人实时结果适合当场看趋势和做会议草稿；需要可归档、可追责的多人 diarization，请上传完整录音走离线 pyannote，并预留人工校对。

**API 用法**（上传文件 + 离线 pyannote）：
```bash
curl -X POST http://localhost:8000/v1/upload \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@meeting.mp3" \
  -F "diarization=pyannote"   # ← 启用离线高准确度
```
